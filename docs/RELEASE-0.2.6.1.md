# MediaFlow 0.2.6.1 — Performance Hardening

## Purpose

This patch hardens the v0.2.6 Progressive LQIP implementation for large Media Libraries and multisite operation without changing the public image URL model or introducing a JavaScript-only lazy loader.

## LQIP generation

- A source image is opened/decoded once per LQIP rebuild. MediaFlow reuses the same WordPress image editor for quality retries and progressively smaller fallback sizes.
- The existing per-image inline budget remains configurable; generation settings continue to determine the placeholder signature.
- Render-only limits do not invalidate generated LQIPs, so changing the per-page byte ceiling does not require a Media Library rebuild.

## Frontend payload guard

Two request-global gates now apply before an LQIP data URI is inserted into HTML:

- Maximum inline LQIPs per request: 8 by default.
- Maximum combined inline LQIP data URI bytes per request: 24,576 bytes by default.

Both counters survive MediaFlow service reconstruction during `switch_to_blog()`, preventing multisite aggregation pages from resetting the allowance.

## Rebuild safety

Tools → MediaFlow uses a default batch of five attachments. A request stops starting new attachments after approximately eight seconds and resumes from the last completed attachment ID on the next AJAX request.

WP-CLI defaults to a smaller slice:

    wp mediaflow lqip-rebuild --limit=100
    wp mediaflow lqip-rebuild --limit=100 --after=12345

Larger explicit limits remain available when the host has sufficient image-processing capacity.

## Filesystem/routing work

Successful `Paths::ensure()` and routing-guard verification are memoized for the current site-scoped Paths instance, reducing repeated directory and guard checks in upload/rebuild loops.

Apache guard migration is now keyed by `MEDIAFLOW_ROUTING_SCHEMA_VERSION` rather than the plugin release version. Feature-only releases therefore do not cause a network-wide guard scan. v0.2.6.1 uses routing schema `3`; the first upgrade performs one compatibility check/migration from the old plugin-version marker.

## Preserved behavior

- Real `src` and `srcset` remain directly browser-discoverable.
- Missing/stale LQIPs are not generated by frontend visitors.
- Static warm-cache delivery remains PHP/WordPress-free.
- The v0.2.5 multisite context re-entry hotfix is preserved.
- The non-blocking global image-processing slot budget is preserved.

## Validation scope

Standalone validation covers PHP syntax, source contracts, single-decode fallback behavior, request-global LQIP budgets, OS encoder-lock contention, Apache guard migration, nested multisite context re-entry, and fixture checks for progressive/baseline JPEG plus interlaced/plain PNG. A real target WordPress/Cloudways environment is still required for GD/Imagick, HTTP server, theme/page-builder, cache-plugin, browser and production-load validation.
